title: Production Deployment
description: Harden the starter Docker Compose configuration for a trusted, single-tenant RelayFold deployment.
---

RelayFold publishes separate orchestrator and worker images as one compatible
release. Use those same images for local and production deployments. Production
differs through configuration, networking, storage, resource limits, and
operational controls rather than through production-specific images.

:::danger[Work in progress]
RelayFold and this deployment guidance are not yet production-hardened. This
page documents known safeguards and remaining responsibilities for evaluation; it is not a production-readiness guarantee or a
complete security baseline.
:::

:::caution
This guide prepares the starter configuration for a trusted, single-tenant
environment. RelayFold does not currently provide native production API
authentication, multi-tenant authorization, or a per-task sandbox for untrusted
code.
:::

The configuration generated by `rf init` is a useful baseline. It already runs
the components as non-root users, uses read-only container filesystems, enables
`no-new-privileges`, drops worker capabilities, publishes only the public API on
the host loopback interface, and keeps the worker API inside the Compose
network.

Before relying on that configuration for persistent workloads, replace its
local defaults:

| Concern | Starter default | Production-like configuration |
| --- | --- | --- |
| Images | Development or mutable release tags | Matching stable versions, preferably pinned by digest |
| Public API | Host loopback | Host loopback behind a TLS-terminating, authenticating gateway |
| Worker API | Private Compose network | Private trusted network; never publish it publicly |
| Namespace mode | Unauthenticated global namespace | Single-tenant global namespace behind external access control |
| Storage | Temporary SQLite under `/tmp` | External MySQL with backups and tested restoration |
| Credentials | One local credential file | Restrictive credential files scoped to each worker pool |
| Worker state | Local bind mounts | Monitored storage with a stable worker host identity |
| Resources | Runtime defaults | Explicit CPU, memory, process, disk, concurrency, and timeout limits |
| Operations | Local logs and restart policy | Central logs, monitoring, alerts, upgrades, and rollback |

## Pin one release

Use the orchestrator and worker images from the same RelayFold release. Pin
digests when the deployment must use exactly the artifact that was reviewed:

```text
RELAYFOLD_ORCHESTRATOR_IMAGE=ghcr.io/parsablelabs/relayfold-orchestrator@sha256:<digest>
RELAYFOLD_WORKER_IMAGE=ghcr.io/parsablelabs/relayfold-worker@sha256:<digest>
```

Keep image selection in `config.env`; do not edit software into a running
container. Test upgrades against a copy of production configuration and data,
and keep the previous image digests available for rollback.

### Standalone orchestrator

Each RelayFold GitHub Release also includes a standalone orchestrator archive
for Linux AMD64 and its SHA-256 checksum. This is an alternative packaging
format for operators who prefer to run the control plane directly under a
service manager:

```text
relayfold-orchestrator-<version>-linux-amd64.tar.gz
relayfold-orchestrator-<version>-linux-amd64.tar.gz.sha256
```

The archive contains the `relayfold-orchestrator` executable. Run it as a
dedicated non-root user with the same environment settings described on this
page. The worker is published only as a container image because its supported
runtime includes Node.js, Agent packages, Git, GitHub CLI, Python, compilers,
and other execution tools supplied by the worker image.

Use the standalone orchestrator and worker image from the same release. See
[RelayFold Releases](https://github.com/parsablelabs/relayfold/releases) for
downloads.

## Put the APIs behind network boundaries

The generated configuration binds the public API to `127.0.0.1:3000`. Preserve
that binding when a reverse proxy or API gateway runs on the host, and expose
only the gateway:

```text
client -> HTTPS gateway -> 127.0.0.1:3000 -> orchestrator
worker ------------------- private HTTP ---> orchestrator:3001
```

Configure the gateway to provide TLS, client authentication, request-size
limits, and rate limits. Do not publish port `3001`; the worker API currently
assumes a trusted private network.

RelayFold's built-in global namespace mode does not authenticate requests. When
`RELAYFOLD_USE_GLOBAL_NAMESPACE=true`, authorization headers are ignored and all
resources belong to `global-namespace`. Until API-key-to-namespace resolution is
implemented, use this mode only for one trusted tenant behind external access
control. It must not be used to represent multiple security tenants.

## Replace temporary SQLite with MySQL

The starter configuration writes SQLite to `/tmp/relayfold.db`, which disappears
with the orchestrator container. Configure an external MySQL database for
durable workflow state:

```text
RELAYFOLD_STORAGE=mysql
RELAYFOLD_STORE_MYSQL_HOST=mysql.internal.example
RELAYFOLD_STORE_MYSQL_PORT=3306
RELAYFOLD_STORE_MYSQL_DATABASE=relayfold
RELAYFOLD_STORE_MYSQL_USERNAME=relayfold
RELAYFOLD_STORE_MYSQL_PASSWORD=<secret>
```

Create the database before starting RelayFold. The database user needs
permission to run RelayFold's migrations and to read and write its tables.
Back up both the database and the deployment configuration, then regularly test
restoration.

The current MySQL adapter does not expose transport-encryption settings. Keep
database traffic on a protected private network until database TLS
configuration is supported.

See [Orchestrator Storage](/relayfold/docs/operations/storage/) for supported
versions, migrations, and persistence behavior.

## Add a Compose production override

Keep the generated Compose file as the release baseline and place local
production changes in a second file. For example:

```yaml title="compose.production.yml"
services:
  orchestrator:
    environment:
      RELAYFOLD_STORAGE: mysql
      RELAYFOLD_STORE_MYSQL_HOST: ${RELAYFOLD_STORE_MYSQL_HOST:?required}
      RELAYFOLD_STORE_MYSQL_PORT: ${RELAYFOLD_STORE_MYSQL_PORT:-3306}
      RELAYFOLD_STORE_MYSQL_DATABASE: ${RELAYFOLD_STORE_MYSQL_DATABASE:-relayfold}
      RELAYFOLD_STORE_MYSQL_USERNAME: ${RELAYFOLD_STORE_MYSQL_USERNAME:?required}
      RELAYFOLD_STORE_MYSQL_PASSWORD: ${RELAYFOLD_STORE_MYSQL_PASSWORD:?required}
      RELAYFOLD_MAX_CONCURRENT_WORKFLOWS: ${RELAYFOLD_MAX_CONCURRENT_WORKFLOWS:-4}
      RELAYFOLD_WORKFLOW_QUEUE_CAPACITY: ${RELAYFOLD_WORKFLOW_QUEUE_CAPACITY:-1024}
      RELAYFOLD_TASK_TIMEOUT_SECS: ${RELAYFOLD_TASK_TIMEOUT_SECS:-900}
    mem_limit: 1g
    cpus: 1.0
    pids_limit: 256
    logging:
      driver: json-file
      options:
        max-size: 20m
        max-file: "5"

  worker:
    environment:
      LOG_LEVEL: info
      RELAYFOLD_FUNCTION_TIMEOUT_MS: ${RELAYFOLD_FUNCTION_TIMEOUT_MS:-900000}
    mem_limit: 4g
    cpus: 2.0
    pids_limit: 512
    logging:
      driver: json-file
      options:
        max-size: 20m
        max-file: "5"
```

The numbers are starting points, not universal recommendations. Set them from
observed workflow behavior and ensure task timeouts cover the expected task
duration.

Add the MySQL values to `~/.relayfold/config.env`, restrict that file to its
owner, and inspect the merged configuration before starting:

```bash
chmod 600 ~/.relayfold/config.env

docker compose \
  --env-file ~/.relayfold/config.env \
  -f ~/.relayfold/docker-compose.yml \
  -f compose.production.yml \
  config --quiet

docker compose \
  --env-file ~/.relayfold/config.env \
  -f ~/.relayfold/docker-compose.yml \
  -f compose.production.yml \
  up -d
```

`rf up` uses only the generated Compose file, so invoke `docker compose`
directly when applying an additional override.

## Scope worker credentials and state

The packaged worker reads
`~/.relayfold/file_credentials.json`. The starter configuration mounts only
that file read-only, but every task executed by the worker belongs to the same
trust domain and may be able to read credentials available inside the worker
container.

Store only the credentials that a worker pool needs. Use separate worker
deployments, credential files, and stable `RELAYFOLD_WORKER_HOST_ID` values for
workloads with different owners or authority. Never mount the Docker socket,
the host root filesystem, or a broad secrets directory into a worker.

Worker workspaces and Agent sessions live outside the read-only image. Preserve
the workspace and cache mounts when workflows need continuity across worker
process restarts. Workers may share a host ID only when they also share the
corresponding workspace and Agent session roots.

See [Task Credentials](/relayfold/docs/operations/credentials/),
[Task Workspaces](/relayfold/docs/operations/workspaces/), and
[Worker Host Pinning](/relayfold/docs/operations/worker-host-pinning/) for the
state and continuity model.

### Repair npm cache permissions

Function dependency installation uses `/home/relayfold/.cache/npm`. If npm
reports `EACCES` or root-owned cache files, repair the existing cache mount
using the worker's runtime UID and GID (both default to `10001`). For the
repository's development Compose stack, run from the repository root:

```bash
docker compose stop worker
docker compose run --rm --no-deps --user 0:0 --cap-add CHOWN \
  --entrypoint chown worker -R 10001:10001 /home/relayfold/.cache/npm
docker compose up -d --build worker
```

For a packaged deployment, supply its Compose file and environment file to
these commands, use its updated worker image, and substitute its configured
`RELAYFOLD_WORKER_UID` and `RELAYFOLD_WORKER_GID` if different. The temporary
repair container changes only npm cache ownership; the normal worker remains
unprivileged. Updated worker images install packages as the worker user so
new cache files have the correct owner. After repair, use the
[task retry endpoint](/relayfold/docs/concepts/workflow-lifecycle/#retry) to
requeue the failed task in the existing workflow, or start a new workflow run.
The failed run does not automatically retry.

## Understand the worker trust boundary

A worker container is a deployment boundary, not a per-task security sandbox.
Function code runs as a child process inside the long-lived worker container,
and approved Agent tools run in that same environment. Read-only filesystems,
dropped capabilities, process limits, and network policy reduce risk, but they
do not isolate mutually untrusted tasks from one another.

Run only trusted workflow definitions and Function code. Separate worker pools
by tenant or trust level and restrict their credentials and network access. A
deployment that accepts untrusted or third-party executable code requires an
additional per-task sandbox architecture that RelayFold does not currently
provide.

## Operate one orchestrator per partition

Run one orchestrator instance for each deployment partition and attach its own
worker pool and storage lifecycle. RelayFold does not provide active-active
orchestrator clustering, so do not run multiple orchestrators against the same
database as replicas.

Scale execution by adding workers. Add independent orchestrator partitions when
you need separate capacity, tenants, regions, or failure domains. Monitor queue
depth, task duration, worker availability, workflow failures, database health,
filesystem usage, and container resource pressure before changing concurrency.

See [Scaling](/relayfold/docs/operations/scaling/) for worker pools and
partitioning, and [Reliability and Side Effects](/relayfold/docs/operations/reliability/)
for retry-safe task design.

## Production readiness checklist

Before accepting persistent workloads:

- pin matching orchestrator and worker release images
- keep the public API behind a TLS and authentication gateway
- keep the worker API and database on trusted private networks
- use external MySQL and test backup restoration
- restrict deployment files and worker credential files to their operators
- give each worker pool only the credentials and network access it needs
- preserve workspace and Agent session storage where continuity is required
- set resource, concurrency, queue, and timeout limits
- centralize logs and alert on health, capacity, and repeated workflow failures
- test upgrades, orchestrator restart recovery, worker loss, and rollback
- run only trusted executable task code
