---
title: Orchestrator Storage
description: Configure in-memory or durable SQL storage for workflow definitions and workflow state.
---

RelayFold stores workflow definitions, function definitions, workflow instances, workflow events, and workflow list summaries through the orchestrator storage adapter.

By default, the orchestrator uses in-memory storage. This is useful for local development, but workflow state is lost when the orchestrator process exits.

## In-memory storage

In-memory storage is the default:

```bash
RELAYFOLD_STORAGE=memory
```

You can also omit `RELAYFOLD_STORAGE`; `memory` is used automatically.

In-memory definitions, workflow state, task state, events, and list results are
isolated by the namespace selected for each request. Reusing the same definition
or workflow ID in another namespace creates an independent in-memory resource.

## Durable SQL storage

Use SQL storage when workflow definitions and workflow state should survive orchestrator restarts.
The selected database adapter initializes its schema automatically on startup. MySQL uses versioned SQLx migrations recorded in the `_sqlx_migrations` table; SQLite retains its existing RelayFold migration metadata.

`RELAYFOLD_STORAGE` selects the adapter directly:

- `sqlite` uses the embedded SQLite adapter.
- `mysql` uses the MySQL adapter.

Other values are not supported.

### SQLite

The parent directory for a SQLite database file must exist and be writable by the orchestrator process.

```bash
RELAYFOLD_STORAGE=sqlite
RELAYFOLD_STORE_SQLITE_PATH=/var/lib/relayfold/relayfold.db
```

The environment generated by `rf init` instead places SQLite at
`/tmp/relayfold.db`. That packaged local database is temporary and is discarded
when the orchestrator stops. Deployments that require durable SQLite storage
must provide a persistent writable directory and configure its path explicitly.

### MySQL

The MySQL adapter supports MySQL 8.0.19 and newer and uses InnoDB transactions for atomic workflow transitions. Create the database before starting RelayFold and grant the configured user permission to run schema migrations and read and write its tables.

```bash
RELAYFOLD_STORAGE=mysql
RELAYFOLD_STORE_MYSQL_HOST=mysql.example.com
RELAYFOLD_STORE_MYSQL_PORT=3306
RELAYFOLD_STORE_MYSQL_DATABASE=relayfold
RELAYFOLD_STORE_MYSQL_USERNAME=relayfold
RELAYFOLD_STORE_MYSQL_PASSWORD=replace-me
```

`RELAYFOLD_STORE_MYSQL_HOST`, `RELAYFOLD_STORE_MYSQL_USERNAME`, and `RELAYFOLD_STORE_MYSQL_PASSWORD` are required and cannot be empty. `RELAYFOLD_STORE_MYSQL_PORT` defaults to `3306`, and `RELAYFOLD_STORE_MYSQL_DATABASE` defaults to `relayfold`. The configured database must already exist, and the configured user needs migration and data privileges.

The development Docker Compose stack connects through `host.docker.internal`
to a separately managed MySQL container whose port is published on the host.
Its Compose file provides local MySQL defaults and includes a commented SQLite
alternative with a persistent Docker volume.

Switching an existing development stack from SQLite does not copy its data into MySQL. The previous `${HOME}/.relayfold/sqlite` files remain on the host, and RelayFold uses the data already present in the configured MySQL database.

RelayFold stores timestamps and workflow versions as signed 64-bit integers. Indexed RelayFold identifiers are limited to 512 ASCII characters by the MySQL schema.

SQL definitions, workflow state, tasks, verifier state, events, and list results
are isolated by namespace. The same resource ID can be used independently in
different namespaces.

Namespace columns are declared as `VARCHAR(36)`, which accommodates both the
built-in `global-namespace` and canonical UUID strings. SQLite treats this
declaration with TEXT affinity and does not enforce the declared length;
namespace validation remains an orchestrator responsibility.

The namespace-aware SQL schema is a destructive compatibility boundary. RelayFold
does not migrate databases created by pre-namespace versions. Before upgrading,
stop the orchestrator and workers, back up state needed for rollback, and
recreate the SQL database. The orchestrator will initialize the current schema
when it next starts.

## Persistence model

SQL storage keeps workflow-level state, task attempts, verifier state, and events in separate tables. RelayFold still exposes the same workflow state model through the API.

Workflow definitions may enter and leave the API as JSON or YAML. Storage
normalizes definition payloads to JSON, so the selected API representation does
not change the persisted format.

Workflow transition commits are atomic: when the orchestrator records a workflow change, the SQL adapter saves the event records, workflow row, task rows, and verifier rows together. Workflow list summaries are derived from workflow and task rows when queried.

### Current state and event history

RelayFold uses a hybrid persistence model, not a fully event-sourced store. The
latest committed workflow state is authoritative and is the normal read and
restart-recovery path. Ordered workflow events record how that state changed and
are available through the [workflow event endpoint](/relayfold/docs/api-reference/#workflow-events)
for historical inspection and debugging.
